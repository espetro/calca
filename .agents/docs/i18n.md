# i18n — Translation Pipeline

Calca uses [intl-ai](https://github.com/sigilco/intl-ai) (Rust binary, run via `bunx intl-ai` — shipped by the `intl-ai` npm package) to manage the web app's locale files. Config lives in [`intl-ai.toml`](../../intl-ai.toml) at the repo root.

## Tier model

- **English (`en`) is tier-1.** It is the only human-authored locale file and the only one a PR must satisfy. `apps/web/messages/en.json` is the source of truth.
- **All other locales are prerelease-only.** Parity is produced by `intl-ai fill` + `intl-ai check` as part of cutting a release (see [versioning.md](versioning.md)) — **not** on PRs, **not** on every build.

**Not wired:** `@intl-ai/unplugin` (or any auto-fill bundler plugin). It calls the model on every build, which contradicts the tier model. Do not add it to `apps/web/vite.config.ts`.

Targets: `es`, `fr`, `de`, `pt-br`, `it`, `nl`, `ja`, `zh-hans`.

## Commands

```bash
bun run i18n:status   # per-locale inventory: missing/stale/modified/extra counts
bun run i18n:fill     # translate missing keys (additive; never overwrites existing values)
bun run i18n:check    # audit; exits non-zero on missing/stale/invalid findings
```

All three need the provider env (every command loads the config, which interpolates it):

```bash
export INTL_AI_BASE_URL=...          # optional; defaults to OpenRouter in intl-ai.toml
export INTL_AI_MODEL=google/gemini-2.5-flash-lite   # any cheap tier model
export INTL_AI_API_KEY=<key>
```

`intl-ai.toml` points at `https://openrouter.ai/api/v1` by default — a full 8-locale fill on a cheap model is well under $1. Any OpenAI-compatible endpoint works; `kind = "command"` (e.g. a local agent CLI) is also supported — see the [providers doc](https://intl-ai.illo.fyi/guide/providers/).

## Where parity runs

1. **Before tagging (the real step):** `bun run i18n:fill && bun run i18n:check`, then commit `apps/web/messages/` + `intl-ai.lock.d/` with the version bump. This is what lands translations *in* the release.
2. **Release workflows (the gate):** the `i18n` job in `release-cli.yml` and a tag-only step in `desktop.yml` run `fill` + `check` on the tag checkout. On an at-parity tag `fill` is a no-op (zero model calls). If it repairs anything, the tag was cut without parity and the job **fails the release** — a tag can't absorb commits, so shipping anyway would publish English-only artifacts. Fix: run `i18n:fill`, commit, re-tag.

### Required CI configuration

- `secrets.INTL_AI_API_KEY` — provider key for the fill step. **Must be created** in GitHub → Settings → Secrets → Actions.
- `vars.INTL_AI_MODEL` — model id (e.g. `google/gemini-2.5-flash-lite`) in GitHub → Settings → Variables.

PR workflows never touch intl-ai; a missing secret only blocks tag builds.

## `intl-ai.lock.d/` — why it's committed

The lockfile directory holds one sorted TOML block per key: source hash, written value, `origin` (`ai`/`human`), and a `reviewed` bit. Committing it makes `fill` incremental (only missing/stale keys are re-translated) and keeps provenance auditable in git — it's designed for diffs and merges (`intl-ai lockfile merge` resolves conflicts union-style, human wins). The local findings cache `.intl-ai/` is gitignored; `intl-ai.lock.d/` is not.

## Human ownership and review

`fill` never overwrites an existing value. To take ownership of a string — or mark one you wrote by hand:

```bash
bunx intl-ai mark --origin human <locale> <key>   # record a key as human-authored
bunx intl-ai review <locale> <key>                # mark reviewed
bunx intl-ai unreview <locale> <key>              # clear the review bit
```

A value that differs from what AI last wrote counts as human-owned automatically: `fill` won't touch it, and a stale source shows up as a `check` finding rather than an auto-rewrite. `check --fail-on unreviewed` exists if we ever want a human-in-the-loop review gate; it's deliberately not in the release gate.

## Release gate scope

`intl-ai.toml` sets `[check] fail_on = ["missing", "stale", "invalid"]` — structural findings only. The LLM `judge` check (quality scoring) is **advisory only** and must stay out of `fail_on`: a provider outage or flaky judge can never block a release.

## Locale tag conventions

All locale tags are lowercase BCP-47: `pt-br`, `zh-hans` — never `pt-BR`, `zh-Hans`. `pt-br` is Brazilian Portuguese (the volume market; `pt-pt` would be a separate target if ever needed); `zh-hans` is Simplified Chinese (`zh-hant` = Traditional, not currently a target). Filenames match: `apps/web/messages/zh-hans.json`.
